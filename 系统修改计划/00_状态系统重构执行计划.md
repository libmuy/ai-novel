## Context

这是一个 AI Agent 驱动的千万字小说生成系统（Obsidian vault + Python 工具）。上一次重构（`0ace7d8`）把逐章链式状态改成「冻结基线 ⊕ 全部履历折叠」的单一权威模型，方向正确，但留下三类问题：

1. **重构遗留的数据污染**：苍玄的整棵状态树、冻结基线、第 01 章履历里的对象是 `角色.叶云生`——骨架模板的示例人物。这本书真正的主角叫**苏砚**（全书 35 个文件用苏砚，0 个用叶云生）。污染早于本次重构（`5b5773f` 已存在），git 历史里从未有过苏砚的真实状态数据，**只能重建，无从恢复**。
2. **三处静默错误**：解析器吞行、描述字段冻结在回溯后语义失效、对象 ID 笔误静默分裂出影子对象。共同特征是**出错时所有工具都报成功**，现有 `audit_consistency.py` 全都查不出来。
3. **模型缺两块**：没有逐章物化的开篇状态；对象关系完全没建模，散在自由文本 / 指针 / 反向指针三种形式，且存在同一事实的双重记录。

**预期结果**：状态的任何不一致都能被脚本检测并一键重建；写章 Agent 打开章节目录即可拿到全部上下文；关系可查询、可精确重放、不可能双边不一致。

## 执行守则（硬规则，违反即停）

1. **一波一提交**。每波做完跑完验证再 commit，不要跨波混提交。commit message 用 `refactor(状态): W<N> <一句话>`。
2. **每一步都先看再改**。改任何文件前先 `cat` / `sed -n` 看当前内容，确认与本文档描述一致；不一致就停下来问人（说明仓库已被改动过）。
3. **禁止 `git add -A`**。逐个 `git add` 明确列出的文件。
4. **不要自作主张扩大范围**。本文档没写的文件不要动。
5. **验证失败不要绕过**。测试红了就修，不要改测试预期去迁就代码，除非本文档明说该波要改预期。
6. **绝不手工编辑派生数据**（`01_最新状态/`、`03_本章开篇状态.md`、各类目索引）。它们由脚本覆盖写。要改内容，改上游的履历然后重折。

### 停止条件（遇到就停下来问人，不要猜）

- 某个 `grep` 的命中数与本文档写的对不上（说明仓库状态与计划假设不符）
- 需要判断小说内容（角色该有多少灵石、某个关系是不是「敌对」）——这是内容创作，不是代码修复
- 需要调用 LLM 但没有 API key（`OPENAI_API_KEY` 或 `02_工具/llm.secret.toml`）
- `audit_consistency.py` 出现本文档没预告过的 `error`

## 设计基线（所有改动服从这一条）

```
权威数据（只有这两样，其余全部可删除重建）
  ├── 05_工作区/00_全局/00_基线状态/          创世快照 · 只读不可变
  └── 05_工作区/…/章NNNN/04_本章状态履历.md    每章增量 · append-only

派生数据（脚本生成，禁止手工编辑，随时可重建、可校验）
  ├── 05_工作区/00_全局/01_最新状态/          当前全量状态
  ├── 05_工作区/00_全局/00_描述合并缓存.jsonl
  ├── 05_工作区/…/章NNNN/03_本章开篇状态.md
  └── 各类目索引 / 卷末快照 / 反向视图
```

**不变量**：任何计算永远从基线出发、重折全部履历。**逐章快照只是这个计算的输出，永远不作为下一步计算的输入。**

> 上一次重构删掉逐章 `03_本章初始状态.md`，正是因为旧模型里它是**计算的输入**（第 N 章初始 = 第 N-1 章初始 ⊕ 第 N-1 章履历），一旦某环出错就无法自愈。本计划重新引入逐章快照，但它是**输出**。文件名改成 `03_本章开篇状态.md`，让这个语义断裂在文件名上可见。

**全量重折的成本已实测**：3000 章（约合千万字）单次折叠 62 ms，写到 3000 章的累计成本约 93 秒。
👉 **不要为省这个引入增量更新或卷末检查点。** 自愈能力比性能重要得多。

### 1.3 章目录排序改造

`state_tree.iter_workspace_changelogs()` 现在用裸的 `found.sort()`——折叠顺序 == 路径字符串顺序，没有任何校验。`章0001` 的两位前缀第 100 章就溢出（`100_章0100` 会排在 `11_章0011` 前面），一次命名偏差就能**静默重排全书历史**，而所有工具都报成功。

```python
# 在文件顶部常量区加
CHAPTER_REL_RE = re.compile(r"^(\d+)_第(\d+)部/(\d+)_卷(\d+)/章(\d+)$")


def chapter_sort_key(changelog_path, novel_dir):
    """从履历路径解析 (部号, 卷号, 章号)。不符合规范即抛错，绝不静默排序。"""
    chap_dir = os.path.dirname(os.path.abspath(changelog_path))
    ws = os.path.join(os.path.abspath(novel_dir), WORKSPACE_DIRNAME)
    rel = os.path.relpath(chap_dir, ws).replace(os.sep, "/")
    m = CHAPTER_REL_RE.match(rel)
    if not m:
        raise StateMergeError(
            f"章目录路径不符合规范: {WORKSPACE_DIRNAME}/{rel}\n"
            f"应为 NN_第NN部/NN_卷NN/章NNNN（例: 01_第01部/01_卷01/章0001）"
        )
    _pp, part, _vp, vol, chap = m.groups()
    return (int(part), int(vol), int(chap))
```
```python
# 改前
def iter_workspace_changelogs(novel_dir):
    ...
    found.sort()
    return found

# 改后
def iter_workspace_changelogs(novel_dir):
    ws = os.path.join(novel_dir, WORKSPACE_DIRNAME)
    found = []
    if not os.path.isdir(ws):
        return found
    for dirpath, _dirs, files in os.walk(ws):
        if CHANGELOG_FILENAME in files:
            found.append(os.path.normpath(os.path.join(dirpath, CHANGELOG_FILENAME)))
    found.sort(key=lambda p: chapter_sort_key(p, novel_dir))
    return found
```

### 2.2 重写 `parse_md_table`

```python
def parse_md_table(file_path, *, strict=True):
    """
    解析 Markdown 状态表格。兼容 4 列（状态文件）与 7 列（履历）。
    strict=True 时，表格区内任何列数不符或类型非法的行都抛 StateMergeError，
    绝不静默丢弃——静默丢行是状态腐烂的头号来源。
    值内的竖线写作 \\| ，解析时还原。
    """
    if not os.path.exists(file_path):
        return []

    records = []
    with open(file_path, 'r', encoding='utf-8') as f:
        lines = f.readlines()

    for lineno, line in enumerate(lines, 1):
        stripped = line.strip()
        if not stripped.startswith('|'):
            continue

        # 先把转义竖线换成哨兵，切分后再还原
        protected = stripped.replace('\\|', '\x00')
        parts = [p.strip().replace('\x00', '|') for p in protected.split('|')[1:-1]]
        if not parts:
            continue

        head = parts[0]
        if (head in ('对象ID', '对象 ID', 'ID')
                or head.startswith(':-') or head.startswith('---')):
            continue

        if len(parts) not in (4, 7):
            if strict:
                raise StateMergeError(
                    f"{file_path}:{lineno} 状态表格行应为 4 列或 7 列，实际 {len(parts)} 列。\n"
                    f"  行内容: {stripped}\n"
                    f"  若某列的值里本身含竖线，请写成 \\| "
                )
            continue

        obj_id, field, ftype, val = parts[0], parts[1], parts[2], parts[3]

        if strict and ftype not in VALID_MERGE_TYPES:
            raise StateMergeError(
                f"{file_path}:{lineno} 未知的类型列「{ftype}」。\n"
                f"  合法值: {sorted(VALID_MERGE_TYPES)}\n"
                f"  常见原因: 用了全角破折号「—」而非半角「-」"
            )

        meta = {}
        for idx, col_name in enumerate(CHANGELOG_META_COLUMNS):
            src_idx = 4 + idx
            if src_idx < len(parts):
                meta[col_name] = parts[src_idx]

        records.append({
            'object_id': obj_id, 'field': field,
            'type': ftype, 'value': val, 'meta': meta,
        })

    return records
```

> ⚠️ 类目索引文件（`01_角色.md` 等）是 3 列，但 `load_state_tree` 会跳过它们、从不调 `parse_md_table`。确认这一点仍成立，不要顺手去「修」索引的列数。

## W3 · 描述字段合并缓存（替换现有的「冻结回写」）

### 问题

`pending_descriptive()` 无条件跳过 `变更类型 == 描述合并` 的行，重放时这些行按字面整体覆盖。但那段冻结文本是对着**首次合并时的旧值**算出来的，**前提没有被记录**。

具体后果：基线 `身体状况 = 健康`，第 5 章写「左臂骨折」，第 10 章写「左臂已愈」。回头把第 5 章改成「右腿被废」后重折——第 10 章那行仍字面覆盖成「左臂已愈，行动如常」，**右腿的伤凭空消失**。结果依然确定性，但语义错了。`state_drift` 也查不出来：它用同一套折叠逻辑算期望值，等于自证清白。技能 `06_章节回溯修改.md` 全程没提示这个风险。

同时 `rewrite_changelog_text()` 把履历「值」列直接换成 LLM 输出，**作者原文没有任何地方留存**（`--backup` 非默认且只备份单章）——对一个有损的 AI 变换做不可逆的原地覆盖。

### 方案

**履历表从此永不被脚本改写**，永远是作者原文。LLM 合并结果存进独立的 append-only 缓存，键上带输入指纹。缓存的键天然包含前提，**「失效」不需要额外检测机制——查不到就是失效**。

### 3.1 `state_tree.py` 新增缓存层

```python
import json  # 加到文件顶部 import 区

MERGE_CACHE_FILENAME = "00_描述合并缓存.jsonl"


def merge_cache_path(novel_dir):
    return os.path.join(novel_dir, WORKSPACE_DIRNAME, "00_全局", MERGE_CACHE_FILENAME)


def value_fingerprint(text):
    """描述文本的内容指纹。取 sha256 前 16 位，足够避免碰撞且便于人眼比对。"""
    return hashlib.sha256((text or "").strip().encode("utf-8")).hexdigest()[:16]


def load_merge_cache(novel_dir):
    """返回 {(对象, 字段, 旧值sha, 新值sha): 合并文本}。文件不存在返回 {}。"""
    path = merge_cache_path(novel_dir)
    cache = {}
    if not os.path.exists(path):
        return cache
    with open(path, encoding="utf-8") as f:
        for lineno, line in enumerate(f, 1):
            line = line.strip()
            if not line or line.startswith("#"):
                continue
            try:
                e = json.loads(line)
                cache[(e["对象"], e["字段"], e["旧值sha"], e["新值sha"])] = e["合并文本"]
            except (json.JSONDecodeError, KeyError) as ex:
                raise StateMergeError(f"{path}:{lineno} 描述合并缓存行损坏: {ex}")
    return cache


def append_merge_cache(novel_dir, entries):
    """追加写。缓存是派生物，只追加不重写、不删除。"""
    if not entries:
        return
    path = merge_cache_path(novel_dir)
    os.makedirs(os.path.dirname(path), exist_ok=True)
    with open(path, "a", encoding="utf-8") as f:
        for e in entries:
            f.write(json.dumps(e, ensure_ascii=False) + "\n")
```

### 3.2 用 `split_descriptive` 替换 `pending_descriptive`

```python
def split_descriptive(base_records, changelog_records, cache):
    """
    把本章履历的描述类变更分成「缓存命中」与「待合并」两拨。
    返回 (resolved, pending)：
      resolved  {(obj, field): merged_text}   —— 可直接用，不调 LLM
      pending   [(obj, field, old, new), ...] —— 需要 LLM

    跳过条件：类型非「描述」；旧值为空/不存在（首次出现，字面写入即可）；新旧文本相同。
    """
    cur = {(r['object_id'], r['field']): r['value'] for r in base_records}
    resolved, pending = {}, []
    for rec in changelog_records:
        if rec['type'] != '描述':
            continue
        key = (rec['object_id'], rec['field'])
        old_val = cur.get(key)
        if old_val is None or old_val.strip() in NUMERIC_EMPTY_VALUES:
            continue
        new_val = rec['value'].strip()
        old_val = old_val.strip()
        if new_val == old_val:
            continue
        ck = (rec['object_id'], rec['field'],
              value_fingerprint(old_val), value_fingerprint(new_val))
        if ck in cache:
            resolved[key] = cache[ck]
        else:
            pending.append((rec['object_id'], rec['field'], old_val, new_val))
    return resolved, pending
```

**删除** `pending_descriptive()`、`rewrite_changelog_text()`、常量 `DESCRIPTIVE_MERGED_MARK`。

### 3.3 重写 `fold_all`

```python
def fold_all(baseline_dir, changelog_paths, *, cache=None, resolver=None, chapter_names=None):
    """
    从冻结基线出发，按给定顺序折叠各章履历。

    cache:        load_merge_cache() 的结果；None 视为空
    resolver:     callable(pending) -> {(obj, field): merged_text}
                  None 且存在未命中 -> 抛 StateMergeError
    chapter_names: 与 changelog_paths 等长的章名列表，仅用于写进缓存条目做溯源

    返回 (records, new_cache_entries)。调用方负责 append_merge_cache。
    **本函数永不修改任何履历文件。**
    """
    records = load_state_tree(baseline_dir)
    cache = cache or {}
    new_entries = []
    today = datetime.now(timezone.utc).date().isoformat()

    for i, cl_path in enumerate(changelog_paths):
        cl = parse_md_table(str(cl_path))
        resolved, pending = split_descriptive(records, cl, cache)

        if pending:
            if resolver is None:
                names = ", ".join(f"{o}.{f}" for o, f, _, _ in pending)
                raise StateMergeError(
                    f"{cl_path} 有 {len(pending)} 处描述字段变更未命中合并缓存: {names}\n"
                    f"  原因：首次合并，或上游章节被改动导致前提变化。\n"
                    f"  处理：对该章跑 merge_chapter_state.py，"
                    f"或 rebuild_global_state.py --merge-pending。"
                )
            merged = resolver(pending)
            for (obj, field, old, new) in pending:
                text = merged[(obj, field)]
                resolved[(obj, field)] = text
                entry = {
                    "对象": obj, "字段": field,
                    "旧值sha": value_fingerprint(old),
                    "新值sha": value_fingerprint(new),
                    "合并文本": text,
                    "章": chapter_names[i] if chapter_names else "",
                    "时间": today,
                }
                new_entries.append(entry)
                cache[(obj, field, entry["旧值sha"], entry["新值sha"])] = text

        records, _diff = merge_states(records, cl, descriptive_resolution=resolved)

    return records, new_entries
```

在每张数据库卡片末尾加：
```markdown
## 动态字段清单
> 声明本对象的哪些属性随剧情变化、需要进入状态追踪。字段名与类型以 03_字段词表.md 为准。

| 字段 | 类型 | 基线初值 |
|---|---|---|
| 境界 | 运算-枚举 | 炼气一层 |
| 内力值 | 运算-数值 | 100 |
```

- `02_卡片模板/` 下人物/势力/资源等卡片模板加这个小节
- 新增 `02_工具/build_baseline.py`：扫全部卡片的该小节 → 生成基线状态树（技能 08 从纯人工变半自动）
- **苍玄现有的 11 张人物卡 + 29 张势力卡要补这个小节**——这一步需要读设定做内容判断，**如果不确定某个字段的初值，留空并报给用户，不要编**

### 4.3 引用完整性校验

实测：履历里写 `角色.苏彦`（笔误），`merge_states` 静默新建一个对象，全流程零告警。**千万字尺度下这是第一大漂移源**——每写错一次名字就分裂出一个影子对象，两者各自累积状态，几百章后无法归并。

audit 新增三条：
- `state_object_unregistered`（error）：对象名必须能在对应数据库分类找到同名卡片
  （角色→`02_数据库/07_人物`、势力→`03_势力组织`、物品→`04_资源`、财务→同名角色/势力、世界→`02_地理区域` 或 `01_设定`）。
  群像/临时对象走显式白名单文件 `05_工作区/00_全局/00_状态对象白名单.md` 放行
- `state_field_undeclared`（error）：状态字段未在该对象卡片的动态字段清单里声明
- `state_object_stateless`（info）：卡片声明了动态字段但从未进入状态

### 验收

故意写一个 `角色.苏彦` 到某章履历，跑 audit 应被 error 拦住；手改一个 `03_本章开篇状态.md` 应触发 `chapter_opener_drift`。

## W5 · 关系建模

> 需强模型。

### 现状问题

关系散在三种互不兼容的形式，且存在同一事实的双重记录：

```
角色.苏砚   | 关键关系 | 描述      | 与赵铁柱交恶      ← 自由文本，无法查询/校验
势力.黑石会 | 主要关系 | 描述      | 与云璃商会敌对    ← 同上
物品.锈铁剑 | 持有者   | 运算-枚举 | @角色.[苏砚]      ← 指针
角色.苏砚   | 持有物品 | 运算-列表 | 锈铁剑,破草鞋     ← 与上一行是同一事实的双重记录
```

最后两行可以各自变化、互相矛盾，没有任何检查。

### A. 非对称关系 → 记在「从属方」的字段上，单边记录，反向由脚本派生

判据：这个事实变化时，只有一方是主动改变的。

```
物品.锈铁剑 | 持有者 | 运算-枚举 | 角色.苏砚
角色.苏砚   | 师承   | 运算-枚举 | 角色.周九算
势力.黑石会 | 隶属   | 运算-枚举 | 势力.冥河殿
```

原则：**一个事实只在一个地方记录**。

具体动作：**删掉 `角色.X | 持有物品` 字段**，只保留 `物品.Y | 持有者`。「苏砚身上有哪些物品」由索引脚本扫所有 `物品.*.持有者` 反查生成，写进 `01_最新状态/01_角色/` 的索引供人查阅——**派生视图，不是权威**。`财务.X | 人情债·债务` 同理改为指向债权人的结构化列表。

### B. 对称关系 → 升为一等对象，规范化无向 ID

敌对/结盟/同门/血亲这类没有从属方，记在任何一边都是任意的，且必然导致双边不一致。

```
05_工作区/00_全局/01_最新状态/06_关系/06_关系_苏砚&赵铁柱.md

| 对象ID | 字段 | 类型 | 值 |
| 关系.苏砚&赵铁柱 | 关系性质   | 运算-枚举 | 敌对 |
| 关系.苏砚&赵铁柱 | 亲疏度     | 运算-数值 | -60 |
| 关系.苏砚&赵铁柱 | 公开程度   | 运算-枚举 | 隐秘 |
| 关系.苏砚&赵铁柱 | 甲对乙态度 | 描述      | 戒备，视为矿场上的威胁 |
| 关系.苏砚&赵铁柱 | 乙对甲态度 | 描述      | 轻蔑，尚未把他当回事 |
| 关系.苏砚&赵铁柱 | 关系概述   | 描述      | 因枯港矿城分矿之争结怨 |
```

**分隔符必须用 ASCII `&`**。理由（不要改成别的）：
- **不能用 `｜`(U+FF5C)**：与 Markdown 表格分隔符 `|` 肉眼几乎无法区分，而 NFKC 规范化会把它转成 `|`——一旦哪个环节做了这步，对象 ID 就在表格第一列炸开成多列
- **不能用 `~`**：`write_state_tree` 已用它做文件名碰撞后缀（`~<sha1[:6]>`）
- **不能用 `+` / `-` / `,`**：与运算-列表语法冲突
- `&` 是 ASCII、文件系统安全、Markdown 无含义、不在 `sanitize_name` 的 `_UNSAFE_NAME_CHARS`（`/\:*?"<>|`）里，会原样进文件名

两端名字**按 Unicode 序排列后**拼接。排序保证同一对关系在物理上只可能有一个文件——**双边不一致从结构上不可能发生**。「甲」「乙」由排序顺序机械确定，用来承载态度上的不对称。

### C. 废除 `关键关系` / `主要关系` 描述字段，内容迁进关系对象

### 改动面

- `state_tree.py`：`CATEGORY_BY_PREFIX` 加 `"关系": "06_关系"`；`CATEGORY_ORDER` / `CATEGORY_LABELS` 同步；新增 `normalize_relation_id()`（拆分、排序、重组）
- `audit_consistency.py`：`STATE_OBJECT_PREFIX_CATEGORY` 同步；新增 `relation_id_malformed`（error：必须恰好含一个 `&`、两端都是已注册对象、必须已排序，报错时给出规范形式）
- `03_字段词表.md`：新增「6. 关系类对象」小节；删除 `关键关系` / `主要关系` / `持有物品`（现有 4 处引用）
- `02_卡片模板/11_状态台账模板.md`（2 处）同步
- `build_state_snapshot.py`：章节快照拉取规则——本章出场对象集合 S，拉取**至少一端在 S 内**的全部关系对象。**不是「两端都在」**：苏砚对不在场仇人的敌意同样影响他本章的行为
- 骨架模板加 `06_关系/` 目录；技能 `03` / `08` 补关系维护说明

**关系粒度规则**（写进字段词表）：只有**会影响剧情决策**的关系才建对象，路人关系不建。这是稀疏图，一本千万字的书大概几百到几千条，完全可控。

### 验收

- `关系.赵铁柱&苏砚`（未排序）被 audit 拦住并提示规范形式 `关系.苏砚&赵铁柱`
- `关系.苏砚&张三`（张三无卡片）被 `state_object_unregistered` 拦住
- 反查视图（某角色持有哪些物品）正确生成
