## 一、 字段合并类型与语法规范

章级状态表格统一包含 4 列：`| 对象ID | 字段 | 类型 | 值 |`。

所有字段划分为以下两大类（4 个细分类型）：

### 1. 运算类字段 (Operation Fields)
运算类字段支持精确计算、原子替换或列表增删。在 `04_本章状态履历.md` 中，其"值"列必须遵守固定语法。

| 细分类型 | 说明 | 履历(Changelog)语法规范 | 合并(Merge)计算规则 |
|---|---|---|---|
| **运算-数值** | 可计算的数值 (如内力值、灵石数、耐久度) | `+N` (增加 N) 或 `-N` (减少 N) | 在初始状态值的基础上累加/累减。如初始 `100`，履历 `-30`，合并终态为 `70`。 |
| **运算-枚举** | 有限固定选项 (如境界、状态、终态标记) | `目标枚举值` | 直接替换为目标枚举值。对象终态可写作固定枚举（如 `活跃` / `死亡` / `退场` / `暂离`）。 |
| **运算-列表** | 集合或列表 (如人情债、主要资产) | `+X,-Y` (添加 X，移除 Y) | 对原列表做元素增删。如初始 `矿场分红权,破草鞋`，履历 `+培元丹,-破草鞋`，合并终态为 `矿场分红权,培元丹`。 |

### 2. 描述类字段 (Description Fields)
自由文本描述，不进行语义逻辑合并。

| 细分类型 | 说明 | 履历(Changelog)语法规范 | 合并(Merge)计算规则 |
|---|---|---|---|
| **描述** | 自由文本 (如外貌变化、当前心境、领地动向) | 自由 Markdown 文本 | **LLM 智能合并**（见下）。首次出现的描述字段直接字面写入。 |

> **描述类字段的智能合并**：整体盲覆盖会丢弃旧描述里未被新描述涵盖的信息。因此当某个
> 「描述」类字段发生实质变更（旧值非空、且新旧文本不同）时，`merge_chapter_state.py` 会把
> 本次全部待合并描述字段打包成**一次** LLM 调用（旧文本 + 新文本合并成不丢信息、不矛盾的
> 一段），把结果连同「对象·字段·旧值指纹·新值指纹」一起追加写进独立的 append-only 缓存
> `05_工作区/00_全局/00_描述合并缓存.jsonl`。**`04_本章状态履历.md` 永不被脚本改写**，
> 永远是作者原文；「变更类型」列不会出现 `描述合并`。
>
> 缓存按 `(对象, 字段, 旧值指纹, 新值指纹)` 做键，天然带前提：重折时旧值指纹对不上
> （因为上游章节被改过）就是缓存未命中，会重新调 LLM 合并，不会拿着过期前提算出的旧
> 合并文本去覆盖新前提下的结果。
>
> - LLM 端点配置见 `02_工具/00_系统级/llm.config.toml`（OpenAI 兼容 `/chat/completions`）；密钥走
>   环境变量或 `02_工具/00_系统级/llm.secret.toml`（已 gitignore）。
> - **LLM 不可用（无配置 / 无 key / 网络失败）且本章确有待合并描述变更 → 合并中止、
>   退出码 2、不写任何文件。** 纯运算章节（无描述变更）无需 key。
> - 回溯重折用 `rebuild_global_state.py`；对含未命中缓存的描述变更的旧章需加 `--merge-pending`。

### 3. 履历元数据列（不参与合并计算）

`04_本章状态履历.md` 在标准 4 列 `| 对象ID | 字段 | 类型 | 值 |` 之后追加 3 个**元数据列**。
它们由 `parse_md_table` 读入但**不参与 `merge_states` 的任何类型合并计算**，仅用于人工检索、
章后审计与「改早期章节」后的级联冲突排查。其他 Agent **不得**把它们当作需要参与类型合并的字段。

- **章节号**：产生该条变更的章节编号，如 `0001`。用于定位变更来源、级联重放时的溯源。
- **变更时间**：该条变更被记录/定稿的日期，如 `2026-08-30`；未知写 `-`。
- **变更类型**：该「对象-字段」在本章的变更性质，枚举 `新建` / `修改` / `移除`。
  - `新建`：该对象-字段本章首次出现；
  - `修改`：在已有值基础上做数值运算、枚举替换、列表增删或描述覆盖；
  - `移除`：该对象-字段在本章后不再追踪（仅标记，合并计算仍按「值」列语法处理）。

`05_工作区/00_全局/01_最新状态/` 每对象文件与 `05_工作区/00_全局/00_基线状态/` 每对象文件为标准 4 列，**不带**这 3 个元数据列。

## 二、 官方注册字段表 (Official Registry)

### 1. 角色类对象 (`角色.[姓名]`)

| 字段名 | 细分类型 | 合法枚举值 / 示例说明 | 适用场景 |
|---|---|---|---|
| **境界** | 运算-枚举 | 凡人 / 炼气一层 / 炼气二层 / 筑基初期 ... | 修为阶段追踪 |
| **身体状况** | 描述 | 健康 / 左臂受创 / 内伤未愈 ... | 伤势与生理状态 |
| **内力值** | 运算-数值 | 数值 (如 `+50`, `-30`) | 消耗性数值/真气 |
| **所在地** | 描述 | 灰壤凡域·墨骨巷 / 云璃坊链 ... | 空间位置追踪 |
| **外貌变化** | 描述 | 眉角多了一道疤 / 穿麻衣黑袍 ... | 形象特征变动 |
| **当前心境** | 描述 | 警惕 / 焦躁 / 坚决 ... | 心理状态变动 |
| **师承** | 运算-枚举 | `@角色.[某某]` / `自学` / `无` | 正统传功来源（非对称，只记徒方；徒弟列表由脚本反查） |
| **隐患·未解代价** | 描述 | 灰毒入髓(三月内须解) ... | 伏笔与生存威胁 |
| **对象终态** | 运算-枚举 | `活跃` / `死亡` / `退场` / `暂离` | 生命/剧本状态 |

> **已废除**（W5）：`持有物品`、`关键关系`。
> - 「某角色身上有哪些物品」不再单独记录，改由脚本扫全部 `物品.X 的「持有者」` 字段反查，
>   写进派生视图 `05_工作区/00_全局/01_最新状态/00_持有物品反查.md`（只读、非权威）。
> - 人际关系迁入**关系类对象**（见下方第 6 节），不再塞进角色的描述字段。
> - `师承` 是**非对称**关系，作为角色字段保留（只记「跟谁学的」这条硬事实）。

### 2. 物品类对象 (`物品.[名称]`)

| 字段名 | 细分类型 | 合法枚举值 / 示例说明 | 适用场景 |
|---|---|---|---|
| **持有者** | 运算-枚举 | `@角色.[示例角色]` / `无人` / `@势力.[示例势力]` | 物品权属变动 |
| **物品状态** | 运算-枚举 | `完好` / `受损` / `损毁` / `封印` / `易主` | 物理状态 |
| **数量·耐久** | 运算-数值 | 数值 (如 `-1`, `+5`) | 数量或耐久度变动 |
| **等级·类别** | 运算-枚举 | 一阶下品法宝 / 消耗性丹药 ... | 物品评级 |
| **附加说明** | 描述 | 剑柄刻有古旧阵纹 ... | 细节描述 |

### 3. 势力类对象 (`势力.[名称]`)

| 字段名 | 细分类型 | 合法枚举值 / 示例说明 | 适用场景 |
|---|---|---|---|
| **综合实力** | 描述 | 微末 / 炼气期小型帮会 / 金丹底蕴 ... | 势力评级变动 |
| **领地·据点** | 描述 | 九曲长街黑市 / 墨骨巷三号坊 ... | 势力范围变动 |
| **隶属** | 运算-枚举 | `@势力.[某某]` / `独立` | 上级势力（非对称，只记下级方；下属列表由脚本反查） |
| **与主角互动状态**| 运算-枚举 | `中立` / `敌对` / `友好` / `隐秘关注` | 互动态度 |
| **当前动向** | 描述 | 正在暗中搜寻废矿坑残页 ... | 剧情推进方向 |

> **已废除**（W5）：`主要关系`。势力间的敌对/结盟等对称关系迁入**关系类对象**（第 6 节）。
> `隶属` 是非对称关系，作为势力字段保留。

### 4. 财务类对象 (`财务.[对象名]`)

| 字段名 | 细分类型 | 合法枚举值 / 示例说明 | 适用场景 |
|---|---|---|---|
| **财富分级** | 运算-枚举 | 赤贫 / 温饱 / 小康 / 富足 / 巨富 | 财力层级 |
| **灵石结余** | 运算-数值 | 数值 (如 `+120`, `-45`) | 基础货币流转 |
| **主要资产** | 运算-列表 | `+墨骨巷小铺面,-旧矿床` | 房产/矿脉等固定资产 |
| **人情债·债务** | 运算-列表 | `+欠陈掌柜50下品灵石` | 财务负债与人情 |

### 5. 世界类对象 (`世界.[主体/规则]`)

| 字段名 | 细分类型 | 合法枚举值 / 示例说明 | 适用场景 |
|---|---|---|---|
| **世界状态** | 描述 | 灰壤灵气进一步衰退 ... | 全局环境变动 |
| **揭示进度** | 描述 | 阶段01(感知异常) -> 阶段02(发现规律) | 法则揭示历程 |
| **异常现象** | 描述 | 墨骨巷月圆之夜阵纹逆转 ... | 局部规则异象 |

### 6. 关系类对象 (`关系.<甲>&<乙>`)

**对称关系**（敌对 / 结盟 / 血亲 / 同门 / 竞争 …——没有从属方、记在任何一边都任意、
必然导致双边不一致）升为一等对象。

**ID 规范**：

- 分隔符**必须是 ASCII `&`**，恰好一个。不能用全角 `｜`（NFKC 会折成 `|` 炸表格）、
  `~`（文件名碰撞后缀）、`+` `-` `,`（运算-列表语法）。
- 两端名字**按 Unicode 码位排序**后用 `&` 拼接：`关系.<排序在前者>&<排序在后者>`。
  排序保证同一对关系物理上只有一个文件——**双边不一致从结构上不可能**。
- 「甲」= 排序在前的一端，「乙」= 排序在后的一端。
- 两端必须都是已注册对象（人物卡 / 势力卡 / 状态对象白名单）。
- 文件：`05_工作区/00_全局/01_最新状态/06_关系/06_关系_<甲>&<乙>.md`。

**字段表**：

| 字段名 | 细分类型 | 合法枚举值 / 示例说明 | 必填 |
|---|---|---|---|
| **关系性质** | 运算-枚举 | `血亲·父子` `血亲·母子` `血亲·兄弟` `血亲·其他` `师徒` `同门` `结盟` `友谊` `交易伙伴` `雇佣` `竞争` `敌对` `血仇` `债务纠葛` `利用` `暧昧` `恩义` | ✅ |
| **亲疏** | 运算-枚举 | `死仇` / `交恶` / `疏远` / `中立` / `友善` / `亲密` / `至亲`（7 档粗粒度；**不用数字**） | ✅ |
| **公开程度** | 运算-枚举 | `公开` / `半公开` / `隐秘` | ✅ |
| **甲对乙态度** | 描述 | 甲（排序在前者）对乙的主观视角，如「戒备，视为矿场上的威胁」 | 选填 |
| **乙对甲态度** | 描述 | 乙对甲的主观视角 | 选填 |
| **关系概述** | 描述 | 一句话来龙去脉，如「因枯港矿城分矿之争结怨」 | ✅ |
| **对象终态** | 运算-枚举 | `活跃` / `终结`（一方死亡/退场或关系彻底了断后标记，供级联检查） | 选填 |

**关系粒度规则**：只有**会影响剧情决策**的关系才建对象，路人关系不建。这是稀疏图，
一本千万字的书大概几百到几千条。

**非对称关系不建关系对象**：物品归属记 `物品.Y 的「持有者」`；正统传功记 `角色.X 的「师承」`；
势力上下级记 `势力.X 的「隶属」`。反向（某人有哪些徒弟/物品、某势力有哪些下属）由脚本反查派生。
师徒 / 同门这类**半对称**（有长幼）仍按对称关系对象处理，长幼靠 `甲对乙态度` 文本承载。

## 三、 唯一权威状态存储 `05_工作区/00_全局/01_最新状态/` 与冻结基线

不再有逐章 `03_本章初始状态.md`。全书状态的唯一权威存储是小说目录下的 `05_工作区/00_全局/01_最新状态/`：
**每个对象一个文件，按类目分子目录**（`01_角色/ 02_物品/ 03_势力/ 04_财务/ 05_世界/ 06_关系/`，
外加兜底 `99_其他/`）。每个文件是标准 4 列表，头两行注明 `> 对象ID:`。

- 对象 ID 前缀 → 类目目录：`角色.→01_角色` `物品.→02_物品` `势力.→03_势力`
  `财务.→04_财务` `世界.→05_世界` `关系.→06_关系`。
- 派生视图（只读、非权威、脚本自动写）：`00_持有物品反查.md`（从 `物品.* 的「持有者」` 反查）。
- `05_工作区/00_全局/01_最新状态/` == 冻结基线 `05_工作区/00_全局/00_基线状态/`
  ⊕（按章节路径顺序折叠全部 `04_本章状态履历.md`）。
- 基线在 `01_设定/`+`02_数据库/` 定稿后、写第 1 章前一次性生成（技能 `08_基线状态初始化.md`），
  之后只读不可变。
- **基线范围**：只登记第 1 章开篇确有状态、且第 1 卷内会登场/被主角博弈的对象；卡片存在但本卷不登场的对象
  不进基线，只在卡片声明「动态字段清单」，等首次登场章的履历里用「新建」引入。详见技能 `08_基线状态初始化.md`。
- 维护脚本：章末 `merge_chapter_state.py --chapter-dir <本章>`；回溯重折
  `rebuild_global_state.py <小说目录>`；某章开篇状态 `build_state_snapshot.py --at-chapter`。
- 一致性由 `audit_consistency.py` 的 `state_drift` / `global_state_*` 检查保证。

格式细节见 `00_通用模板/02_卡片模板/15_全局状态模板.md`。
